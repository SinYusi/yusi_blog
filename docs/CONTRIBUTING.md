# 작업 흐름

모든 작업은 이슈에서 시작해 PR로 끝납니다. `main`과 `dev`에 직접 push하지 않습니다.

## 브랜치 구조

| 브랜치                     | 역할                                            | 배포                   |
| -------------------------- | ----------------------------------------------- | ---------------------- |
| `main`                     | 운영 코드. 릴리스 PR로만 변경                   | Vercel 운영 환경       |
| `dev`                      | 개발 통합 브랜치. 저장소의 기본 브랜치          | Vercel 미리보기        |
| `<type>/<이슈번호>-<설명>` | 이슈 작업 브랜치. `dev`에서 만들고 `dev`로 머지 | PR마다 Vercel 미리보기 |

```
feat/12-post-list ─┐
fix/15-dark-mode  ─┼─(squash merge)→ dev ─(릴리스 PR, merge commit)→ main
chore/2-workflow  ─┘
```

## 역할

| 담당               | 역할                                                       |
| ------------------ | ---------------------------------------------------------- |
| 사용자             | 작업 지시, PR 최종 확인과 머지, 릴리스 시점 결정           |
| Claude             | 이슈 작성부터 리뷰 반영까지 (아래 1~7단계), 릴리스 PR 작성 |
| CodeRabbit, Gemini | PR 자동 리뷰                                               |

## 흐름

```
이슈 생성 → 브랜치 생성 → 작업 → PR 생성 → AI 리뷰 → 리뷰 반영 → (사용자) 머지
```

1. **이슈 생성:** 이슈 템플릿 중 하나로 이슈를 만들고, 템플릿의 필수 항목을 채웁니다. 로드맵 단계에 맞는 마일스톤을 연결합니다.

   | 템플릿 | 라벨            | 필수 항목                  |
   | ------ | --------------- | -------------------------- |
   | 기능   | `enhancement`   | 목적, 작업 내용, 완료 기준 |
   | 버그   | `bug`           | 현상, 재현 방법, 기대 동작 |
   | 작업   | `chore`         | 목적, 작업 내용, 완료 기준 |
   | 문서   | `documentation` | 목적, 작업 내용, 완료 기준 |

2. **브랜치 생성:** 최신 `dev`에서 이슈 번호를 포함한 브랜치를 만듭니다.
3. **작업:** 작업 단위마다 커밋합니다. 커밋하기 전에 `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm build`를 통과시킵니다.
4. **PR 생성:** `dev`를 대상으로 PR을 만듭니다. PR 템플릿을 채우고, 본문에 `Closes #이슈번호`를 넣어 머지되면 이슈가 자동으로 닫히게 합니다.
5. **AI 리뷰:** PR을 열면 CodeRabbit과 Gemini가 자동으로 리뷰합니다. 이후 push에는 자동 리뷰가 실행되지 않으므로(CodeRabbit 한도 절약), 리뷰가 달리지 않거나 다시 받아야 하면 코멘트로 요청합니다.
   - CodeRabbit: `@coderabbitai review` (무료 플랜은 시간당 1회). 설정은 `.coderabbit.yaml`: 한국어, 원인과 근거 중심 설명, 리뷰 중점(성능, 접근성, 디자인 토큰 준수), PR 제목 형식 검사(실패 시 에러), 이슈 반영도 평가(경고)
   - Gemini: `@gemini-cli /review` (뒤에 중점 사항을 덧붙일 수 있음)

   CodeRabbit은 시간당 1회로 제한되므로, 변경 범위에 따라 머지 전에 필요한 리뷰를 구분합니다.

   | 변경 범위                                                                    | 머지 전 필수 리뷰   |
   | ---------------------------------------------------------------------------- | ------------------- |
   | 코드, 워크플로(`.github/`), 설정·의존성(`package.json`, `next.config.ts` 등) | CodeRabbit + Gemini |
   | 문서만 (`docs/`, `*.md`, 이슈·PR 템플릿)                                     | Gemini              |
   - CodeRabbit이 필요한 PR이 여러 개면 위험도가 높은 PR(워크플로, 보안, 인증, DB)부터 리뷰를 받습니다.
   - 리뷰어가 준 **코드 제안(수정안)을 그대로 적용한 커밋**은 다시 리뷰받지 않아도 됩니다.
   - 지적한 방향대로 고쳤더라도 **코드를 직접 작성했다면** 다시 리뷰받습니다. 새 변경을 더한 경우도 마찬가지입니다.
   - CodeRabbit 한도에 걸리면 안내된 해제 시각 이후에 다시 요청합니다. 한도는 PR을 열 때의 자동 리뷰에도 쓰이므로, 리뷰를 기다리는 PR이 있으면 새 PR은 그 뒤에 엽니다.

6. **리뷰 반영:** 지적 사항을 검토합니다.
   - 타당하면 수정하고, 스레드에 반영한 커밋을 답글로 남긴 뒤 스레드를 해결 처리합니다.
   - 반영하지 않으면 그 이유를 답글로 남깁니다.
7. **머지 요청:** CI 통과, 리뷰 반영이 끝나면 사용자에게 머지를 요청합니다.
8. **머지 (사용자):** Squash and merge로 `dev`에 머지하고 작업 브랜치를 삭제합니다.

## 릴리스

`dev`에 모인 변경을 운영에 반영할 때 진행합니다.

1. 사용자가 릴리스를 지시하면, Claude가 `dev` → `main` PR을 만들고 `release` 라벨을 붙입니다. 제목은 `release: vX.Y.Z — <요약>`, 본문에는 포함된 PR 목록을 적습니다.
2. CI와 Vercel 미리보기를 확인합니다.
   - 릴리스 PR은 **AI 리뷰를 다시 받지 않습니다.** 포함된 PR은 모두 `dev`에 머지되기 전에 필요한 리뷰를 거쳤고, 릴리스 PR에서 새로 생기는 코드는 없습니다. CodeRabbit과 Gemini도 `dev` 대상 PR만 리뷰하도록 설정되어 있습니다.
   - 단, `main`에만 있는 커밋이 있어 충돌을 해결했다면 그 해결 내용은 리뷰 대상입니다.
3. 사용자가 **Create a merge commit**으로 머지합니다. Squash하면 `dev`와 `main`의 이력이 어긋나 다음 릴리스에서 충돌이 생기므로 사용하지 않습니다. 머지 커밋 메시지는 다음 형식을 따릅니다.

   ```
   release: vX.Y.Z — <요약> (#<릴리스 PR 번호>)

   - <포함된 PR 제목> (#<번호>)
   - ...
   ```

4. 머지되면 Claude가 `main`의 머지 커밋에 annotated 태그(`vX.Y.Z`)를 붙이고 GitHub Release를 만듭니다.
   - 릴리스 노트: 맨 위에 이번 릴리스의 **하이라이트** 요약을 쓰고, 그 아래에 자동 생성 목록을 붙입니다. 자동 목록은 PR을 라벨별로 분류하며(`.github/release.yml`), `release` 라벨이 붙은 릴리스 PR 자신은 제외됩니다.
   - 운영 도메인에 배포된 커밋이 태그와 같은지 확인합니다.

### 버전

`vMAJOR.MINOR.PATCH` 형식을 따릅니다.

| 올리는 자리 | 기준                                                                                      |
| ----------- | ----------------------------------------------------------------------------------------- |
| MINOR       | 기능이 추가된 릴리스                                                                      |
| PATCH       | 버그 수정, 설정·문서 변경만 있는 릴리스                                                   |
| MAJOR       | `v1.0.0`은 로드맵 3단계(독자 기능)까지 마치고 블로그를 공개 운영할 때. 그 전까지는 `v0.x` |

- 첫 릴리스는 0단계 완료 시점의 `v0.1.0`입니다.

## 저장소 보호 규칙

위 흐름은 저장소 설정(ruleset)으로 강제됩니다. 규칙에 예외(우회 권한)는 두지 않습니다.

| 규칙                                   | `dev`    | `main`         |
| -------------------------------------- | -------- | -------------- |
| 직접 push 금지 (PR 필수)               | ✅       | ✅             |
| CI(`Lint, typecheck, build`) 통과 필수 | ✅       | ✅             |
| 리뷰 스레드를 모두 해결해야 머지 가능  | ✅       | ✅             |
| 브랜치 삭제, force push 금지           | ✅       | ✅             |
| 허용 머지 방식                         | Squash만 | Merge commit만 |

- AI 리뷰(CodeRabbit, Gemini)는 필수 체크로 두지 않습니다. 시간당 한도나 일시적 오류로 머지가 막히지 않게 하기 위해서이며, 대신 위 5단계의 규칙으로 지킵니다.
- 1인 저장소라 본인 PR을 승인할 수 없으므로 "리뷰 승인 필수"는 두지 않습니다.
- 머지하면 작업 브랜치는 자동으로 삭제되고, Squash 커밋의 제목은 PR 제목이 됩니다.

## 마일스톤

로드맵(`docs/ROADMAP.md`)의 각 단계가 마일스톤입니다: `0단계: 기반` … `5단계: 최적화와 회고`. 모든 이슈와 PR은 해당 단계의 마일스톤에 연결합니다.

## DB 스키마 변경

스키마는 `src/db/schema.ts`에 정의하고, 마이그레이션 파일(`drizzle/`)로 적용합니다. 배포 시 적용 방식은 [ADR-0006](adr/0006-migrate-on-deploy.md)을 따릅니다.

| DB (Neon 브랜치)        | 적용 시점                                     |
| ----------------------- | --------------------------------------------- |
| `dev`                   | 로컬에서 `pnpm db:migrate`                    |
| `preview/<작업 브랜치>` | PR 미리보기 배포의 빌드 단계 (`vercel-build`) |
| `main` (운영)           | 운영 배포의 빌드 단계 (`vercel-build`)        |

1. `src/db/schema.ts`를 수정합니다.
2. `pnpm db:generate --name <변경-내용>`으로 마이그레이션을 만들고, 생성된 SQL을 직접 읽어 의도와 맞는지 확인합니다.
3. `pnpm db:check`로 **마이그레이션 대상**이 운영이 아닌 `dev` 브랜치인지 확인한 뒤, `pnpm db:migrate`로 적용하고 동작을 확인합니다. `db:check`는 앱 쿼리 대상과 마이그레이션 대상을 모두 보여 주고, 둘이 다른 DB면 실패합니다.
4. 스키마와 마이그레이션 파일을 함께 커밋하고 PR을 엽니다. PR 미리보기 배포가 성공하면 운영 데이터 복제본에서도 마이그레이션이 적용된 것입니다.

지켜야 할 것:

- 이미 적용된 마이그레이션 파일은 수정하지 않습니다. 고칠 것이 있으면 새 마이그레이션을 만듭니다.
- 이전 코드와 호환되지 않는 변경(열·테이블 삭제, 이름 변경, NOT NULL 추가)은 **추가 → 코드 전환 → 제거** 순서로 여러 릴리스에 나눕니다. 마이그레이션은 새 코드보다 먼저 적용되므로, 한 번에 바꾸면 배포 중인 이전 코드가 깨질 수 있습니다.
- 운영 DB에 로컬에서 직접 마이그레이션을 실행하지 않습니다.

## 브랜치 이름

```
<type>/<이슈번호>-<짧은-설명>
```

예: `feat/12-post-list-page`, `fix/15-dark-mode-flash`, `chore/2-git-workflow`

| type       | 용도                     |
| ---------- | ------------------------ |
| `feat`     | 새 기능                  |
| `fix`      | 버그 수정                |
| `perf`     | 성능 개선                |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test`     | 테스트 추가, 수정        |
| `docs`     | 문서                     |
| `chore`    | 설정, 빌드, CI, 의존성   |

## 커밋 메시지

[Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/) 형식을 따르고, 요약은 한국어로 씁니다.

```
<type>(<scope>): <요약>

<본문: 무엇을 왜 바꿨는지 (선택)>
```

- type은 브랜치 type과 같습니다. CI 설정 변경에는 `ci`도 씁니다.
- scope는 선택입니다. 예: `feat(editor): 슬래시 커맨드 추가`

## PR

- 제목은 커밋 메시지 형식을 따릅니다. Squash merge를 하면 PR 제목이 dev의 커밋 메시지가 됩니다.
- 하나의 PR은 하나의 이슈만 다룹니다.
- 성능, 번들 크기, 접근성 수치가 바뀌면 PR의 성과 기록 표와 `docs/ROADMAP.md` 성과 기록 표에 남깁니다.

## 라벨

| 라벨            | 용도                             |
| --------------- | -------------------------------- |
| `enhancement`   | 기능                             |
| `bug`           | 버그                             |
| `chore`         | 설정, CI, 의존성 등 기능 외 작업 |
| `documentation` | 문서                             |
| `performance`   | 성능 측정, 최적화                |
| `accessibility` | 접근성                           |
| `design`        | 화면 설계, 디자인 시스템         |
| `release`       | `dev` → `main` 릴리스 PR         |
