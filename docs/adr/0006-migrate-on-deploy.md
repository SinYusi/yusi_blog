# 0006. 배포 빌드 단계에서 DB 마이그레이션 적용

- 상태: 승인
- 날짜: 2026-09-28

## 배경

스키마는 drizzle-kit 마이그레이션 파일(`drizzle/`)로 관리한다. 로컬(`dev` 브랜치)에서 만든 마이그레이션을 미리보기 DB 브랜치와 운영 DB(`main`)에도 빠짐없이 적용해야 한다. 적용을 잊으면 새 코드가 옛 스키마를 만나 장애가 난다.

## 선택지

1. **배포 빌드 단계에서 적용**: Vercel 빌드 명령을 `drizzle-kit migrate && next build`로 둔다.
2. **수동 적용**: 릴리스할 때 사람이 운영 DB에 직접 실행한다.
3. **GitHub Actions에서 적용**: 머지나 릴리스 시 워크플로가 실행한다. 운영 DB 자격 증명을 GitHub에도 저장해야 한다.

## 결정

배포 빌드 단계에서 적용한다. `package.json`의 `vercel-build` 스크립트(`drizzle-kit migrate && next build`)를 Vercel이 기본 빌드 명령 대신 실행한다.

- **미리보기에서 먼저 검증된다.** Neon 연동이 PR 미리보기마다 운영 DB를 복제한 브랜치를 만들고, 그 빌드에서 마이그레이션이 적용된다. 운영 데이터 복제본 위에서 마이그레이션이 한 번 실행된 뒤에야 머지·릴리스된다.
- **적용을 잊을 수 없다.** 운영 배포(`main`)에서도 같은 명령이 실행된다.
- **자격 증명이 한곳에 있다.** DB 연결 정보는 Vercel-Neon 연동만 관리하고, GitHub에는 두지 않는다.
- GitHub Actions CI는 `pnpm build`(마이그레이션 없음)를 그대로 쓴다.

## 결과

- 마이그레이션이 실패하면 배포가 실패한다. 반쯤 적용된 스키마로 새 코드가 배포되는 것보다 안전하다.
- 마이그레이션은 되돌리기 어렵다. 열·테이블 삭제나 이름 변경처럼 이전 코드와 호환되지 않는 변경은 한 번에 하지 않고, **추가 → 코드 전환 → 제거**의 여러 릴리스로 나눈다 (docs/CONTRIBUTING.md의 DB 스키마 변경 절차).
- 이미 적용된 마이그레이션 파일은 수정하지 않는다. 고칠 것이 있으면 새 마이그레이션을 만든다.
- 빌드 시간에 마이그레이션 확인 시간(변경이 없으면 짧음)이 더해진다.
- 1단계에서 페이지가 빌드 중 DB를 조회하게 되면, DB가 없는 GitHub Actions CI의 빌드를 어떻게 할지 정해야 한다 (#20에서 결정).
