# 0006. 배포 빌드 단계에서 DB 마이그레이션 적용

- 상태: 승인
- 날짜: 2026-09-28

## 배경

스키마는 drizzle-kit 마이그레이션 파일(`drizzle/`)로 관리한다. 로컬(`dev` 브랜치)에서 만든 마이그레이션을 미리보기 DB 브랜치와 운영 DB(`main`)에도 빠짐없이 적용해야 한다. 적용을 잊으면 새 코드가 옛 스키마를 만나 장애가 난다.

## 선택지

1. **배포 빌드 단계에서 적용**: Vercel 빌드 명령을 `drizzle-kit migrate && next build`로 둔다.
2. **수동 적용**: 릴리스할 때 사람이 운영 DB에 직접 실행한다.
3. **GitHub Actions에서 적용**: 머지나 릴리스 시 워크플로가 실행한다. 운영 DB 자격 증명을 GitHub에도 저장해야 한다.

## 결정

배포 빌드 단계에서 적용한다. `package.json`의 `vercel-build` 스크립트(`tsx scripts/migrate.mts && next build`)를 빌드 명령으로 쓴다. Vercel이 `vercel-build`를 기본 빌드 명령보다 우선하는 동작에 기대지 않도록 `vercel.json`의 `buildCommand`에 `pnpm vercel-build`를 명시한다.

- **미리보기에서 먼저 검증된다.** Neon 연동이 PR 미리보기마다 운영 DB를 복제한 브랜치를 만들고, 그 빌드에서 마이그레이션이 적용된다. 운영 데이터 복제본 위에서 마이그레이션이 한 번 실행된 뒤에야 머지·릴리스된다.
- **적용을 잊을 수 없다.** 운영 배포(`main`)에서도 같은 명령이 실행된다.
- **자격 증명이 한곳에 있다.** DB 연결 정보는 Vercel-Neon 연동만 관리하고, GitHub에는 두지 않는다.
- GitHub Actions CI는 `pnpm build`(마이그레이션 없음)를 그대로 쓴다.

## 결과

- **동시 실행 직렬화**: 같은 DB 브랜치를 대상으로 빌드가 동시에 돌면(PR에 연달아 push 등) 두 실행이 모두 새 마이그레이션을 미적용으로 판단해 한쪽이 DDL 충돌로 실패한다. `scripts/migrate.mts`는 Postgres advisory lock을 잡은 뒤 적용 이력을 읽어, 나중 실행이 기다렸다가 이미 적용된 것을 확인하고 넘어가게 한다. 세션 잠금이므로 커넥션 풀러를 거치지 않는 직접 연결을 쓴다.
  - 검증(2026-09-28, dev 브랜치): 테스트 마이그레이션을 두 프로세스로 동시에 적용 — 잠금 없이는 한쪽이 `duplicate key value violates unique constraint`로 실패, 잠금을 쓰면 나중 실행이 705ms 기다린 뒤 둘 다 성공.
- **연결 주소 규칙 공유**: 앱 쿼리 대상과 마이그레이션 대상의 선택 규칙을 `src/db/connection-urls.ts` 한곳에 두고 drizzle-kit 설정·마이그레이션·`db:check`가 함께 쓴다. 두 대상은 엔드포인트와 데이터베이스 이름을 모두 비교하며, 다르면 `db:check`는 실패하고 마이그레이션 스크립트는 DB에 연결하기 전에 중단한다. 배포 빌드는 `db:check`를 거치지 않으므로 마이그레이션 스크립트가 직접 확인한다.

- 마이그레이션이 실패하면 배포가 실패한다. 반쯤 적용된 스키마로 새 코드가 배포되는 것보다 안전하다.
- 마이그레이션은 되돌리기 어렵다. 열·테이블 삭제나 이름 변경처럼 이전 코드와 호환되지 않는 변경은 한 번에 하지 않고, **추가 → 코드 전환 → 제거**의 여러 릴리스로 나눈다 (docs/CONTRIBUTING.md의 DB 스키마 변경 절차).
- 이미 적용된 마이그레이션 파일은 수정하지 않는다. 고칠 것이 있으면 새 마이그레이션을 만든다.
- 빌드 시간에 마이그레이션 확인 시간(변경이 없으면 짧음)이 더해진다.
- PR 미리보기 빌드에서는 마이그레이션 뒤에 시드도 실행한다(`tsx scripts/seed.mts --preview-only`). 운영을 복제한 미리보기 DB가 비어 있으면 화면을 확인할 수 없기 때문이다. 시드는 운영 환경에서 실행을 거부한다.
- 1단계에서 페이지가 빌드 중 DB를 조회하게 되면, DB가 없는 GitHub Actions CI의 빌드를 어떻게 할지 정해야 한다 (#20에서 결정).
