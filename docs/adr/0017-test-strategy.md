# 0017. 테스트 전략: 단위·컴포넌트는 Vitest, E2E·접근성은 CI의 임시 DB에서 Playwright, 성능은 미리보기 배포에서 Lighthouse

- 상태: 제안
- 날짜: 2026-11-07

## 배경

4단계(품질)의 완료 기준은 "성능이나 접근성 기준에 미달하면 PR이 실패한다"이다. 로드맵 항목은 Vitest + Testing Library, Playwright E2E(작성 → 발행 → 노출), Storybook, 접근성 점검(axe), Lighthouse CI다. 시작하기 전에 무엇을 어떤 도구로 어디서 돌릴지 정한다.

지금 상태와 제약은 다음과 같다.

- 단위 테스트는 순수 함수 3개 파일 38개(`post-input`, `search`, `post-stats-input`)이고, `node:test` + `tsx`로 CI(`pnpm test`)에서 돈다. React 컴포넌트 테스트는 없다.
- CI는 빌드하지 않는다. 빌드 검증은 DB에 붙는 Vercel 미리보기 배포가 맡는다(ADR-0007).
- 미리보기 배포는 배포마다 Neon 브랜치를 만들어 마이그레이션·시드한다(ADR-0006). 인증 환경 변수가 없어 관리자 경로는 404다. 따라서 미리보기 배포로는 "작성 → 발행" 흐름을 시험할 수 없다.
- Neon 무료 요금제는 브랜치 수 한도가 있다. 실제로 한도에 걸려 미리보기 배포가 실패한 적이 있다.
- `/design` 페이지가 디자인 토큰(색, 글자, 반경, 중단점) 견본을 보여 준다.
- 클라이언트 상호작용이 복잡한 컴포넌트는 검색 창, 조회수·좋아요(잠금·버전·여러 탭), 태그 입력, 목차다. 여기서 리뷰 지적과 회귀가 가장 많이 나왔다.

## 선택지

**A. 단위·컴포넌트 테스트 러너**

1. **`node:test` 유지, 컴포넌트 테스트는 하지 않음**: 의존성이 늘지 않는다. 클라이언트 컴포넌트의 회귀는 리뷰와 E2E에만 맡긴다.
2. **Vitest로 통일**(jsdom + Testing Library): 컴포넌트를 DOM에서 렌더링하고 상호작용을 시험할 수 있다. 기존 테스트는 `node:assert`를 그대로 쓸 수 있어 `describe`/`it` import만 바꾸면 옮겨진다. 개발 의존성이 몇 개 는다.
3. **둘 다 사용**(순수 함수는 `node:test`, 컴포넌트는 Vitest): 옮길 것은 없지만 러너와 명령이 둘이 된다.

**B. E2E를 어디서, 어떤 DB로 돌릴지**

1. **Vercel 미리보기 URL 대상**: 인프라가 필요 없고 실제 배포와 같은 빌드다. 관리자가 404라 "작성 → 발행 → 노출"은 시험할 수 없고 공개 화면만 본다.
2. **GitHub Actions에서 빌드·실행, DB는 실행마다 Neon 브랜치를 만들고 지움**: 전체 흐름을 시험할 수 있다. 인증은 테스트용 `AUTH_SECRET`·`ADMIN_GITHUB_ID`로 서명한 세션 쿠키를 넣는다(GitHub 로그인을 거치지 않음). Neon API 키를 GitHub 비밀값으로 둬야 하고, 실행이 끝나면 브랜치를 지워 한도를 지킨다. CI가 몇 분 길어진다.
3. **CI의 Postgres 컨테이너**: Neon 계정이 필요 없다. 앱이 쓰는 `@neondatabase/serverless`(HTTP 드라이버)는 일반 Postgres에 바로 붙지 않아 프록시를 따로 띄워야 한다. 운영과 다른 경로를 시험하게 된다.

**C. 접근성 점검**

1. **E2E 안에서 axe(`@axe-core/playwright`)**: 공개 화면과 관리자 화면을 E2E가 여는 김에 검사한다. 심각도 `serious`·`critical`이 있으면 실패시킨다.
2. **Lighthouse의 접근성 점수만**: 따로 할 일이 없지만 점수 하나로 뭉뚱그려져 무엇이 문제인지 알기 어렵다.

**D. Lighthouse CI**

1. **미리보기 배포가 끝나면 그 URL로 실행**(`deployment_status` 이벤트): DB·비밀값이 필요 없고, 실제로 배포될 빌드를 측정한다. 미리보기에 Vercel 배포 보호가 켜져 있으면 자동화 우회 비밀값이 필요하다.
2. **B-2의 CI 빌드를 측정**: 같은 실행에서 끝나지만 Vercel 엣지·이미지 최적화·캐시가 없어 운영과 수치가 다르다.

**E. Storybook**

1. **도입**: 컴포넌트를 상태별로 문서화하고 시각 회귀 도구와 잇기 쉽다. 설정·스토리 작성·유지 비용이 든다.
2. **하지 않음**: 1인 블로그라 컴포넌트를 공유할 사람이 없고, 토큰 견본은 `/design` 페이지가 이미 맡는다. 상태별 확인은 컴포넌트 테스트가 맡는다.

## 결정

**A-2 + B-2 + C-1 + D-1 + E-2**를 추천한다.

- **단위·컴포넌트(Vitest):** 기존 순수 함수 테스트를 옮기고, 상호작용이 복잡한 클라이언트 컴포넌트(검색 창, 조회수·좋아요, 태그 입력, 목차)만 컴포넌트 테스트를 쓴다. 모양만 그리는 컴포넌트는 시험하지 않는다.
- **E2E(Playwright, CI):** PR마다 Neon 브랜치를 만들어 마이그레이션·시드하고, `next build && next start`로 띄운 뒤 "관리자 작성 → 발행 → 공개 목록·상세·검색에 노출"과 공개 화면 주요 경로를 시험한다. 끝나면 브랜치를 지운다(실패해도 지우도록 `always()`).
- **접근성(axe):** E2E가 여는 화면마다 axe를 돌려 `serious`·`critical`이면 실패시킨다.
- **성능(Lighthouse CI):** 미리보기 배포 URL로 홈·글 목록·글 상세를 3번씩 측정해 중앙값이 기준에 못 미치면 실패시킨다.
- **Storybook:** 하지 않는다. 로드맵 항목은 이 결정을 가리키도록 고친다.
- Sentry·Vercel Analytics는 테스트가 아니라 운영 관측이라 이 ADR에서 다루지 않는다.

## 결과

- 얻는 것: 리뷰에서 반복된 클라이언트 경합·회귀를 테스트로 고정한다. 관리자부터 공개 화면까지 실제 DB로 한 번에 시험한다. 성능·접근성 기준이 PR 체크가 되어 4단계 완료 기준을 만족한다.
- 감수하는 것: 개발 의존성이 는다(Vitest, jsdom, Testing Library, Playwright, axe, Lighthouse CI). CI 시간이 E2E만큼 길어진다. Neon API 키를 GitHub 비밀값으로 두고, 브랜치 한도를 E2E와 미리보기 배포가 나눠 쓴다. Lighthouse는 미리보기 배포를 기다려야 결과가 나온다.

## 정해야 할 것

1. 기존 `node:test` 테스트를 Vitest로 옮길지(A-2), 둘 다 쓸지(A-3).
2. E2E용 Neon API 키를 GitHub 저장소 비밀값으로 둘지(B-2). 키 발급과 비밀값 등록은 사용자가 한다.
3. Lighthouse 기준값. 추천: 성능 0.9, 접근성 0.95, 권장 사항 0.9, SEO 0.95(모바일 기준).
4. Storybook을 하지 않을지(E-2).
5. 브랜치 보호 규칙의 필수 체크에 E2E·Lighthouse를 넣을지. 규칙 변경은 사용자가 한다.
