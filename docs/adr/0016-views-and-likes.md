# 0016. 조회수·좋아요: posts 테이블의 카운터와 브라우저 요청

- 상태: 승인
- 날짜: 2026-10-15

## 배경

3단계에서 글 상세에 조회수와 좋아요(낙관적 업데이트)를 붙인다(SPEC: "클라이언트 컴포넌트 + Server Action, 정적 페이지 안의 동적 영역만 분리"). 지금까지의 공개 기능은 모두 읽기 전용이라 이 기능에서 처음으로 정할 것이 생긴다.

- 글 상세는 정적 생성되고 글을 저장할 때만 다시 만들어진다(ADR-0013). 방문마다 바뀌는 숫자를 페이지 HTML에 넣으면 정적 생성이 깨진다.
- DB는 Neon 무료 요금제다(ADR-0005). 쓰지 않으면 잠들었다가 요청이 오면 깨어나므로, 방문마다 DB를 부르면 사용 시간(compute)이 방문량에 비례해 는다.
- 로그인 없는 공개 사이트라 "누가 눌렀는지"를 확실히 알 수 없다. 중복 방지는 어느 정도까지만 가능하다.
- `posts` 테이블에는 이미 `view_count`, `like_count` 열과 0 이상 제약이 있다(1단계 스키마).

## 선택지

**저장 위치**

1. **`posts`의 기존 열을 원자적으로 증가**(`update posts set view_count = view_count + 1`): 새 테이블·서비스 없음. 쓰기가 글 행을 건드려 `updated_at`과 섞이지 않게 주의해야 한다(카운터 갱신은 `updated_at`을 바꾸지 않음).
2. **별도 카운터 테이블**(`post_stats`): 글 행과 분리되어 잠금 경합이 없다. 이 규모에서는 이점이 작고 마이그레이션이 는다.
3. **외부 키-값 저장소(Upstash Redis 등)**: DB를 깨우지 않는다. 서비스·계정·비밀값이 하나 는다.

**조회 집계와 중복 방지**

- A. 페이지를 열 때마다 서버에서 증가: 정적 페이지라 서버 코드가 돌지 않는다(불가).
- B. **브라우저가 글을 연 뒤 한 번 요청**(`navigator.sendBeacon`/`fetch`)하고, 같은 브라우저의 같은 글은 3시간에 한 번만 보낸다(`localStorage`에 마지막 집계 시각). 봇 대부분은 스크립트를 실행하지 않아 걸러진다. 저장소를 지우면 다시 센다(정확한 순방문자 수가 아니라 "대략의 읽힘").
- C. 서버가 방문자 식별값(IP·UA 해시)으로 중복을 막는다: 더 정확하지만 개인정보 처리 고지가 필요하고 저장할 것이 는다.

**좋아요 중복 방지**

- D. **브라우저 저장(`localStorage`)만**: 같은 브라우저에서 다시 누르면 취소(토글). 저장소를 지우면 다시 누를 수 있다.
- E. 익명 방문자 쿠키(무작위 id) + `post_likes(post_id, visitor_id)` 고유 제약: 쿠키를 지우지 않는 한 한 번만 센다. 테이블·쿠키가 는다.

**정적 페이지에서 값 보여 주기**

- F. **클라이언트 컴포넌트가 화면에 들어온 뒤 숫자를 받아 그림**(Route Handler, 캐시하지 않음): 글 HTML은 그대로 정적이다. 숫자 자리는 처음부터 같은 크기로 잡아 레이아웃 이동이 없게 한다.
- G. Cache Components의 동적 구멍(`<Suspense>` 안에서 요청 시 렌더링): 정적 껍데기는 유지되지만 방문마다 서버 렌더링·DB 조회가 생긴다.

## 결정

**1 + B + D + F**를 추천한다. 1인 블로그에서 조회수·좋아요는 "대략 얼마나 읽혔나"를 보여 주는 장식에 가깝고, 정확도를 위해 개인정보·테이블·서비스를 늘릴 이유가 작다.

- 조회: 글을 열고 본문이 화면에 들어오면 `POST /api/posts/{id}/view`를 한 번 보낸다(같은 브라우저·같은 글은 3시간에 한 번). 서버는 공개 글인지 확인하고 `view_count`를 1 올린다.
- 좋아요: 버튼을 누르면 숫자를 먼저 바꾸고(낙관적 업데이트) `POST /api/posts/{id}/like`(취소는 `DELETE`)를 보낸다. 실패하면 되돌리고 알린다. 누른 상태는 `localStorage`에 둔다.
- 표시: 조회수·좋아요 수는 숫자 영역이 화면에 가까워지면 `GET /api/posts/{id}/stats`로 받는다. 글 HTML·OG·sitemap에는 넣지 않는다.
- 남용 방지: 요청은 공개 글에만 받고, 같은 IP에서 짧은 시간에 몰리는 요청은 Vercel 방화벽의 rate limiting 규칙으로 막는다(요청 기록은 저장하지 않음). Hobby 요금제에는 규칙이 허용한 요청 1,000,000건이 포함되고, 넘으면 Hobby 사용량 한도 정책을 따른다.
- 카운터 갱신은 `updated_at`을 바꾸지 않는다(sitemap·RSS 수정 시각, 관리자 저장의 동시 수정 검사(ADR-0014)에 섞이지 않게). 스키마의 `updatedAt`에는 `$onUpdate`가 있어 값을 빼면 자동으로 바뀌므로, 갱신할 때 `updated_at`에 기존 값(`set updated_at = updated_at`)을 명시해 넣는다. 공개 페이지 캐시(`posts` 태그)도 무효화하지 않는다.
- SPEC 렌더링 전략 표의 조회수·좋아요 행("클라이언트 컴포넌트 + Server Action")은 이 결정(Route Handler)에 맞게 구현 PR(#94)에서 고친다. SPEC은 구현된 동작을 적는 문서라 구현과 함께 바꾼다.

## 결과

- 얻는 것: 새 테이블·서비스·개인정보 없이 시작한다. 글 페이지의 정적 생성과 첫 화면 성능은 그대로다.
- 감수하는 것: 조회수는 브라우저 기준 근사값이고, 좋아요는 저장소를 지우면 다시 누를 수 있다. 방문마다 DB가 깨어나 Neon 사용 시간이 방문량에 비례해 는다(무료 한도에 다가가면 3번 외부 저장소나 집계 지연으로 옮긴다).
- 숫자는 화면에 들어온 뒤 채워지므로 처음에는 자리만 보인다.
- 좋아요 취소(`DELETE`)는 서버가 누른 사람인지 확인할 수 없어, 누른 적 없는 호출자도 반복해서 보내면 좋아요 수를 깎을 수 있다(0 아래로는 내려가지 않음). 방화벽 규칙은 한 IP의 짧은 폭주만 막으므로 느린 요청이나 여러 IP의 요청은 못 막는다. 좋아요는 장식에 가까운 숫자라 이 위험을 감수하고, 실제로 훼손되면 E(익명 방문자 쿠키 + `post_likes` 고유 제약)로 옮겨 서버가 누른 기록이 있는 요청만 취소하게 한다.

### 결정한 세부 사항 (2026-10-15)

1. 좋아요는 같은 브라우저에서 다시 누르면 취소된다(토글).
2. 조회수는 공개 글 화면에도 숫자로 보여 준다. 관리자 대시보드의 글별 통계(SPEC)는 이후 작업으로 둔다.
3. 같은 브라우저·같은 글의 조회는 3시간에 한 번만 센다. 하루에 여러 번 다시 읽는 것은 다시 세되, 새로고침·뒤로 가기로 바로 늘지 않게 하는 정도의 간격이다.
